32. Architecture -> OPTION C. A Setl8 backend ("evaluator", one hot key) runs all trading off-chain using Stork prices: netting, floors, SL/TP, pending orders, holding fees. Solana holds the trading JOURNAL: after trades close, the evaluator posts the events together with the signed Stork price proofs (`post_journal`), hash-chained and sequence-checked. The chain re-checks arithmetic and money bounds only; it cannot see the true price path. Safety against a wrong or hacked backend = public journal + off-chain verifier, a 2-day delay before any payout, a veto, a daily payout cap, and the vault's own caps. SUPERSEDES decision 21 (keepers, bounty pool, permissionless crank) and the on-chain order/crank design of the first draft (kept in git commit 29221e7 as a possible later hardening, "option B"). Also changes decision 1 wording: positions and orders are no longer stored on-chain. Rovik, 2026-10-09: "isnt the trading supposed to be a backend thing?? only the trading journal is to be updated in the solana public records", then chose 'C: backend + signed prices + payout delay (Recommended)'. Claude warned: under C the evaluator key is trusted for trader outcomes; the chain cannot prove a missed breach or a forged pass; money is bounded by the delay, veto, daily cap and vault caps.
33. Payout delay and veto -> a pass for phases 2 to 5 is a REQUEST first (`request_advance`); the vault payout claim is queued only by `finalize_pass`, callable by anyone after 2 days. Both admins together may `veto_pass` while it is pending. A veto only cancels the pending pass; it cannot create, approve or move money. Phase 1 to 2 (no money) advances immediately, no delay. Rovik, 2026-10-09: 'Both admins together (Recommended)' and '2 days (Recommended)'. Consequence documented: the account is frozen for trading during the 2 days (a pass checked against state that can still change would be meaningless), and the vault's own heartbeat adds up to 5 more days.
34. Daily payout circuit breaker (Claude's call, no question asked) -> `finalize_pass` refuses once the payouts finalized in the current rolling window would exceed `max_payout_per_window` (both-admin setting, window 86,400 s). Value to be set by Rovik (OPEN_QUESTIONS). It is a brake on a compromised evaluator, not a rule for traders; a refused finalize is retried after the window rolls.
35. Evaluator powers (Claude's call, documented) -> evaluator key can only: post journal batches, report a fail, confirm or reject a pass request (confirm only starts the delay; the evaluator compares its engine state with the chain before confirming), and refresh vault activity for a trader. A trader can cancel an unanswered request after 1 hour. It can never request or finalize a payout, cannot open accounts, and cannot change config. Rotation needs both admins. A compromised key can still fabricate journals (see DESIGN 4.7); that is the accepted risk of option C.
36. Coordinated hedging is prohibited: opposite positions in the SAME market across accounts or wallets of one person or group (correlated markets not covered). Process: backend detects and HOLDS the flagged accounts (`hold_account`, evaluator, reversible); both admins review; confirmed -> both admins `fail_for_violation` each account (vault `flag_trader_failed`, wallet banned) and `ban_wallet` linked wallets, no refund or reset; not confirmed -> both admins `release_hold`; `unban_wallet` needs both admins. Rovik, 2026-10-09: 'two wallet hedging is not allowed', then 'Opposite position in same market, and pause them until review'. Claude warned once: detection is heuristic (evasion by sizes, timing, correlated markets, fresh wallets; false matches pause honest traders until review). Because the fail needs both admins, a stolen evaluator key can only hold accounts, not fail or ban them. Also confirmed: the 2-day delay is the scrutiny window for passes; the watchdog (M9) makes it practical.
