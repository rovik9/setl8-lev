## 1. Method (this file)

* Every expected number comes from an independent integer reference written in the test file (`u128`/`i128`, plain `/` and `%`; `ref_ask`, `ref_bid`, `ref_pnl`, `ref_credit`, `ref_holding`, `ceil_mul_div`, thresholds written by hand in `hand()`). The engine is called as a second opinion wherever the prompt says "exactly the engine's number" (price, pnl, credit, `apply_closed_slice`, `check_tight_start`, `holding_fee_micro`, `swap_fee_micro`, `payout_micro`, `frac_exact`, `shared reset_price`).
* Direction is asserted by cross-multiplication, not by the reference's division (ceiling `c` of `n/d`: `c*d >= n` and `(c-1)*d < n`; floor: `f*d <= n < (f+1)*d`).
* Every refusal asserts the exact `Setl8Error` code at the program instruction (so a panic or abort, which shows as `ProgramFailedToComplete`, fails the test), that no `EventLog` was emitted, and that the world is byte-identical afterwards (raw 207 account bytes plus the harness digest of config, wallet, vault state and records, rule sets, markets; for the pass flow `pass_digest`, which adds the payout claims and the tally).
* Every accepted case rebuilds the expected 207 bytes (`assert_account_is`: the old account, the chain head from the real `journal_types::apply_batch`, and exactly the named fields) and compares byte for byte. "Nothing else changed" is therefore checked, not assumed.
* Random streams use splitmix64 with the fixed seed `0x5E78_4D12_A21F_0A06`; each test derives its stream from the seed and its name, and prints both with `--nocapture`.
* Account bytes are edited (as `edit_account` does in the other suites) to reach states that need years of journal or that the program cannot write itself: `size_s`, `b`, `q_tally`, `seq`, `trades_closed`, `last_batch_time`, `pass_requested_at`, `pass_proposed_at`, `vetoes`, the tight fields, the config window, the tally account, the half-spread of the rule set. These states are not reachable by honest play (S = 0, `b = i64::MAX`, ...); their point is that the program must answer with a named error and not panic or wrap. Each is flagged in the test.

## 4. Where a rounding or a missing check is NOT against the trader (LIMITED, pinned)

1. Buy price from a floored oracle value. DESIGN 7.4: "Oracle price to e12: floor; ask = ceil, bid = floor". The program floors the 18-decimal proof value to e12 BEFORE the spread, so a buy is priced from a mid that is lower by up to 1 e12 unit than the exact oracle value: for `quantized = 1,999,999` the program accepts the buy at 2 although the exact ask would be 3 (`oracle_value_edges_are_floored_and_bounded` pins it; a price of 3 is refused). The bias is at most `qty / 1e12` micro-USD per fill in the trader's favour (about 1 micro-USD for 1,000,000 EUR); sells are floored too, so they are against the trader. This is the written design, not a defect; it is the only place where a rounding can favour a buyer.
2. The program does not recompute holding fees or commission: any `Fee` amount up to `i64::MAX` is debited. The ceiling of the fee is the verifier's check (DESIGN 9.3, trust-matrix). Engine side: the property tests show the engine's fee is a ceiling.
3. Margin, average entry, SL/TP and the notional cap are not checked on-chain (`Market.max_notional_usd` is stored by `create_market` but never read by `post_journal`). A fill of `u64::MAX - 615` units at the largest price is accepted although the engine's own notional overflows `i128`. OFF-CHAIN: evaluator and verifier. (Plus ARI-3 below for `qty > i64::MAX`.)
4. A close of any quantity with a correct pnl is accepted: whether the position exists is off-chain.
5. Engine-level pins from `rounding_properties.rs`: the evaluator's commission is a double ceiling (in 8,732 of 100,000 random cases it exceeds the exact single ceiling by at most `ceil(rate/1e6)` micro-USD: against the trader); `holding_fee_micro` returns `Overflow` for `nights == 0` when `q x mark x rate >= 2^128` although the exact fee is 0 (368 of 100,000 cases; the evaluator must not call it with 0 nights); `notional_micro` truncates toward zero (ARI-2).

## 7. What I could NOT test, and why

* The 50,000-iteration LiteSVM fuzz loop with random instruction data and account permutations (prompt item 6, second half) is not part of this fragment; this file is the deterministic extremes half. Panic freedom of the program is shown here only for the paths listed above.
* `swap_fee_micro` overflow through `open_account` and `reset_account` is unreachable: `MAX_FEE_BPS = 1000` bounds the fee below the cost, so its `MathOverflow` cannot happen through the program (engine-level overflow rows are in `rounding_properties.rs`).
* Breach `lock_until = time + 12 h` overflow is unreachable through the program: it needs an event time within 12 h of `i64::MAX`, but a proof timestamp is a `u64` of nanoseconds (about 1.8e10 seconds), so such an event is `ProofTooOld` first. The same bound makes `proof time` arithmetic safe.
* `q_tally` near `i64::MIN` (a negative tally) is not tested: the program never writes one and the tally is documented as never negative.
* Mutation sensitivity: I did not run cargo-mutants on these tests (the `.so` must not be rebuilt by this task). The tests are written to fail if a control is removed (every rounding test accepts exactly one price and refuses its two neighbours; every limit test has both sides), and ARI-3/ARI-4 show the harness really does fail when the program is looser than the design.
* The cluster-clock tests set the LiteSVM clock to values no real cluster will show (`i64::MAX - 1`); they prove checked arithmetic, not a reachable scenario.
* The holding-fee formula itself, the commission, the margin and the notional cap are off-chain and are checked by the engine property tests, the evaluator and the verifier; nothing on-chain can reject a wrong fee amount below `i64::MAX`.
