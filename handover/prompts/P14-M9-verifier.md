TWO STAGES, two commits
STAGE 1 (formats, chain, event replay, intents)
1. Input formats, defined and documented in handover/verifier-formats.md and used verbatim by the later evaluator harness (M10), each with a version field and a test vector:
   - EVENT LOG: JSON Lines. Each line mirrors the program's `EventLog` record: `{ "account": base58, "seq": u64, "event": hex, "proof": hex or "", "slot": u64 }` (the raw canonical bytes the program emitted via `emit_cpi!`; no re-encoding). Also accept the `Opened` record (account, trader, challenge_id, size_s, ruleset_version, genesis_hash) so a verifier can start from the account's birth, and the pass events (`PassRequested`, `PassConfirmed`, `PassRejected`, `PassVetoed`, `PhaseAdvanced`, `PassFinalized`, `AccountFailed`, `ViolationFail`) as typed lines.
   - ACCOUNT SNAPSHOT (optional): JSON of the on-chain `TradingAccount` fields (the 207-byte layout) to compare the replayed final state with the stored one (`b, q_tally, latch, tight_on, r, g_peak, l_level, lock_until, seq, journal_hash, flat, phase, status, trades_closed`).
   - RULES FILE: JSON export of the rule set the account snapshotted (leverage per class, holding fee per class, commission per class, half-spread per market, fee_bps, tier sizes) and the markets (id, class, feed id, max_age_secs, sessions, status, quantity step and minimum, max notional). Define it so it can be produced from the program's `RuleSet` and `Market` accounts.
   - SAMPLE ARCHIVE: one append-only logical stream for all markets (segments per UTC day are allowed; the stream is their concatenation) of fixed-width little-endian records with a versioned header. Each record carries: market id, source byte, source timestamp (ns), `quantized_value` (i128, 18 decimals, the same number a `PriceProof` carries), the evaluator's receive time, and the 32-byte blob digest for source 3 (zeros otherwise). `Meta.samples_hash` = sha256 of the stream PREFIX the batch used; since the Meta carries no length, the verifier finds the prefix length by hashing incrementally and testing every record boundary (O(n), one pass); no boundary matching is a finding. Pick a record size that fits the fields, document the byte table, and write the writer in the crate (M10 will use it).
   - INTENTS FILE: JSON Lines `{ "nonce": u32, "order": hex, "sig": hex }`; `order` is the canonical bytes of an `OrderIntent` that you define in the crate (kind: market, limit, stop, close, cancel, set_sl_tp; market id; side; qty; limit or stop price; sl; tp; client time) with a byte table; the signed message is `b"SL8LEV|" ++ account (32 bytes) ++ b"|" ++ nonce (u32 LE) ++ b"|" ++ order bytes`, signature ed25519 by the TRADER pubkey (taken from `Opened`). `Meta.intents_hash` = sha256 of the file prefix, found the same way. A `Fill` or `Close` event's `intent_id` equals the intent `nonce`; `intent_id == 0` is allowed only for events the evaluator originates (SL/TP triggers, breach and fail closes, flips follow their intent).
2. Library API (pure): `verify_account(inputs) -> Report`, `Report { verdict: Valid | Mismatch, findings: Vec<Finding>, per_phase: Vec<PhaseVerdict>, per_pass: Vec<PassVerdict> }`, `Finding { class, seq, event index, expected, found, message }`. Finding classes (stable names, each with its own tests): `HashChain`, `SequenceGap`, `BadGenesis`, `EventDecode`, `ProofFeed`, `ProofAge`, `PriceMismatch` (event price vs proof mid + spread, using `engine::claims`), `ArchiveMissing` (a proof's value/time not found in the archive), `SamplesHashMismatch`, `IntentsHashMismatch`, `ForgedTrade` (no matching signed intent, or intent says another side/quantity/market), `BadIntentSignature`, `PnlMismatch`, `CreditMismatch`, `QuickMismatch`, `FeeMismatch` (holding and commission expected from `engine::cost`: wrong amount, missing night, fee on a flat day), `MarginMismatch`, `AvgEntryMismatch`, `FloorMismatch` (TightStart/FloorRaised/Breach fields), `StateMismatch` (snapshot vs replay), `EngineVersion`, `UnknownEvent`.
3. Replay for stage 1: rebuild positions and the `AccountState` event by event with `engine::apply_fill`, `check_close`, the cost functions and the claims checks, independently of the program code. A mismatch continues the replay where possible (collect up to 1,000 findings) and sets the verdict `Mismatch`.
4. CLI `setl8-verify`: `setl8-verify account --events E.jsonl --rules R.json --archive A.bin --intents I.jsonl [--snapshot S.json] [--second-archive B.bin] [--json] [--as-of-seq N]`; exit codes 0 Valid, 1 Mismatch, 2 input error. Human text by default, stable JSON with `--json`. `--as-of-seq` replays only up to a pass request (the watchdog use of DESIGN 4.6).

Tests for stage 1 (each named): vector files in crates/verifier/tests/vectors/ produced by a small test-only generator that uses the REAL engine and journal-types (not the verifier code), including the DESIGN 4.9 example as files (fill, tight start, raise, breach, close) that verifies VALID with the 4.9 numbers; each finding class has a tamper test that changes exactly one thing and must produce exactly that class (altered price by 1 e12 unit, forged trade, wrong fee by 1 micro, wrong pnl by 1 micro, dropped event, reordered events, flipped hash bit, wrong genesis, missing night of holding fee, wrong intent signature, intent for another market, archive record altered, wrong `samples_hash`, wrong `intents_hash`, extra unknown event). 8. Pass verdicts: for every `PassRequested` / `PassConfirmed` in the log produce `PassVerdict { phase, requested_seq, valid: bool, reasons }` by replaying to that point and checking the engine's `pass_check` (b >= 1.08 S, flat, phase not failed) and the stored `b`, `seq`, `journal_hash` carried in the event.
