D1 (finding 1, a pending order that only reduces). D2 (finding 2, quick-limit overshoot). The closing slice that pushes the phase quick tally over its limit carries NO commission Fee: the program forbids anything but the `Fail` after it (I-8) and the phase is over. The verifier must NOT expect a Fee after that slice. For a flip whose CLOSING slice overshoots, the opening remainder is not executed (the account fails first): the verifier must accept "trades under intent N end at the Fail" (no ForgedTrade) for exactly this case. Still caught: (a) a missing Fee after a close that does NOT overshoot -> FeeMismatch; (b) a Fee posted after the overshoot -> the program refuses it (keep tests-rs finding_2) and the verifier flags it too; (c) a flip that drops its remainder when the closing slice did not overshoot -> ForgedTrade; (d) a Fail(PhaseQuick) whose preceding slice did not overshoot -> the existing quick/fail finding.
D3 (finding 3, margin refusal at a pending fill). The verifier computes margin sufficiency for a triggered pending order itself, with the same engine function and inputs the evaluator uses (DESIGN 7.3, decision 27), at the trigger sample. If margin is insufficient: it expects NO fill and no event for that order (the order stays pending); if sufficient: it expects the fill. Still caught: (a) an order that had enough margin but has no fill -> TriggerMissed; (b) an order that did not have enough margin but was filled -> a margin finding (reuse the closest existing class, or add `PendingFillWithoutMargin`; say which); (c) an order refused for margin at one sample that later passes margin and triggers again is expected to fill then (it stays pending), and a test pins that.
D4 (finding 4, breach whose forced closes end at or below the static floor or over the quick limit). The verifier replays the breach closes with the engine and, if the resulting B is at or below the applicable static floor, expects `Fail(StaticFloor)` instead of `Breach`; if the closes push the phase quick tally over its limit it expects `Fail(PhaseQuick)`. (The program already demands exactly this: `BreachBelowStaticFloor` 6077, `MustReportFail`.) Order of checks: static floor first, then quick limit, as the program does; confirm against the program source and say so. Still caught: (a) a posted Breach whose closes end at or below F_s -> a finding (the program also refuses it); (b) a posted Fail(StaticFloor) at a sample where E > F_s and no breach closes would end at or below it -> existing class; (c) an omitted Breach/Fail -> MissedBreach as today.
D5 (finding 5, PassFinalized + PhaseAdvanced). The program emits both for one `finalize_pass`. The verifier treats a `phase_advanced` that directly follows a `pass_finalized` of the same account with the same new phase number as a no-op confirmation (idempotent). Any other `phase_advanced` that does not match a pending state change still gives StateMismatch. Document this in handover/verifier-formats.md (an indexer may mirror both). Still caught: a phase_advanced to a different phase, a duplicated one, or one without a preceding pass_finalized/phase-1 confirmation.
