CONTEXT
The backend (built by another team in setl8-back) hosts the unchanged evaluator. It reports five requirements. Review EACH against the current implementation BEFORE proposing anything: confirm, refine or refute it, with file and line. Their text (summarised; read docs/UPSTREAM.md for the original):
R1. Historical market/feed/status configuration updates. `Evaluator::rules()` returns `&RulesCfg` over a private `Rc<RulesCfg>`; there is no public way to apply a market feed change, a status change or a config change at a point in the history, although the verifier's log and rules already model `market_feed_changed` and `market_status_changed` (handover/verifier-formats.md, crates/verifier/src/log.rs, rules.rs, walk.rs). Needed: a deterministic time-ordered API, with clear ordering against samples and orders of the same second, old-history proof identity, and what happens to market tracking (clear or retain).
R2. Versioned, COMPLETE checkpoint/restore plus safe retention. The evaluator privately holds samples, archive, tracks, marks, nonces, intents, queue, buckets and the incremental hash state; nothing public restores it. Needed: a versioned deterministic checkpoint covering internal queues, second buckets, samples, nonce history, archive/intent hash state and prefix counters, lifecycle state; safe retention boundaries so that history is not unbounded; and (if sensible) support for a feed store shared between accounts.
R3. Complete deterministic OUTCOMES. `refuse()` keeps the detail of only the first 256 execution refusals (eval.rs; the unit test `only_the_first_256_refusals_are_kept` pins it); cancel and SL/TP operations, and triggered pending orders, have no journal event and so no completion outcome the host can read. Needed: a drainable outcome stream, not bounded by count, with nonce, arrival/execution/trigger/completion status and reason, deterministically sequenced, WITHOUT changing any trading decision or any journal byte.
R4. Stale public documentation: crates/evaluator/src/lib.rs still says 200,000 CU and "newest sample that existed when they arrived"; the real behaviour is the compute model (compute.rs, handover/backend-compute-contract.md) and decision 68 (D-F08: the newest sample at or before the event second; a triggered order at the trigger sample).
R5. Lifecycle hosting preconditions: `phase_started` mutates state directly, without checking a chain transition, clearing or validating positions, or authenticating anything; the same for `pass_resolved`, `set_held`, `end_externally`. Needed: the canonical preconditions and the phase-end contract, so the host can automate lifecycle safely.
ALSO CHECK (raised by me): the evaluator holds `Rc<RulesCfg>` and `Box<dyn IntentVerifier>` without a Send bound, so `Evaluator` is not `Send`: how does the backend host it across threads or tasks (read their code), and should the canonical type become Send (Arc, `Send` bound on the verifier) as part of this change?
