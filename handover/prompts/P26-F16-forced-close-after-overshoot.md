THE PROBLEM
When a quick-limit fail forces all open positions closed, I-8 rejects every batch that continues after the first close that pushes q_tally above 0.028 S unless the last event is Fail{PhaseQuick}, and I-11 requires the batch to end flat. With several open positions whose quick credits individually add up past the limit (the E-03 story: 3 x 0.5 M EUR + 1 M EUR, +0.6 %: the two smallest credits already exceed 0.028 S) no batch the program accepts can close the account: the evaluator counts it as `unpostable` and the account can never be failed on-chain.

THE DECISION (Rovik's owner-side default: option (a); record it as decision 69)
Relax I-8 narrowly: once q_tally exceeds 0.028 S in a batch, the ONLY events allowed before the final `Fail{PhaseQuick}` are `Close` events whose reason is `Fail` (the forced close-all of the remaining positions, each still applied exactly with the engine functions: pnl, fees and credits are computed as for any close), then `Fail{PhaseQuick}`, then `Meta` with `flat == 1` (I-11 unchanged). Any Fill, any Close with another reason, any other event type after the overshoot is still rejected. The Fail's `b_after` must equal the balance after all these closes (I-11 unchanged). The `StaticFloor` fail path is NOT changed. The evaluator keeps its best-possible close ordering (smallest quick credit first) but may now emit the overshooting close anywhere in the sequence; the verifier must accept the same sequences and must still flag a forced close that no rule justifies (class ForcedCloseUnjustified from P25b: it must now accept Close{Fail} after an overshoot ONLY when the overshoot happened in the same batch and the close belongs to the open positions).
