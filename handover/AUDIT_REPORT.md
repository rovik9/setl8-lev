# M12 audit report: adversarial suite and self-audit of setl8-lev-trading

**Read this first.** The builder of this program (an AI assistant working for Rovik) wrote the program, the evaluator, the verifier and the tests, and
then attacked them with the tests described below. That is a self-audit: the attacker and the author share the same blind spots. It found real defects
(section 4: 7 fixed, 32 open or accepted), so it is not worthless, but **it does not replace an independent human review, and nobody should put real money
behind this program before one has happened** (section 8 says where to start). The words "blocked" and "limited" below mean "this test passes",
nothing more.

Short version of the result:
* The program has no panic, no unchecked arithmetic and no `unsafe` in code a caller can reach (section 12); 50,000 fuzz iterations with a
  fixed seed found no invariant violation and no panic; every instruction refused every wrong signer and every wrong account that the tests tried, with the
  account bytes unchanged.
* The big risks are the ones the DESIGN already names: the evaluator key can fabricate prices and fees (R-1, R-4, R-7); it is bounded by the 2-day delay,
  the veto, the daily cap and the vault (32 % of size per record chain, measured: section 6) and by **the watchdog actually running**.
* The public verifier is weaker than the DESIGN text suggests (findings F-08 to F-14: it does not tie an execution to the sample that justifies it, it can
  be switched off by one poison archive record, signed intents can be reused across batches). Nothing on chain depends on it, but the veto does.
* Nothing in this report was verified by anyone who did not write the code.

## 1. Scope and method

* **Subject:** commit 3b48bfd of branch main (program `programs/setl8-lev-trading`, `crates/engine`, `crates/journal-types`, `crates/evaluator`,
  `crates/verifier`, `tools/launch-config`; vault fixture `tests-rs/fixtures/core_vault.so` sha256 42c6267008ca25cfd7b71792f3797307292049d91420dbba8fe07dc3098c89a6, not rebuilt).
* **Method:** (1) DESIGN 13.2 attacks A-1..A-18 as executable tests; (2) a who-may-call table written by hand from DESIGN 14; (3) account confusion and hygiene
  tables for every instruction; (4) journal and chain attacks; (5) a hand-written state-machine table; (6) engine rounding properties, program arithmetic
  extremes and a LiteSVM fuzz loop; (7) the vault boundary and the R-1 money bound with the real vault; (8) a dishonest-evaluator table, one named test per
  trust-matrix row, verifier malformed inputs and an ed25519 audit; (9) four independent read-only reviewers who saw only source and DESIGN, whose 77 claims
  were each triaged; (10) mutation testing of the program; (11) a unsafe/panic/cast/dependency sweep.
* **Fragments:** every item has a detailed fragment in `handover/audit/` (appendix A). This report summarises; the fragments carry the test names and tables.
* **What "blocked" means here:** the test asserts the exact error code and that every watched account is byte-identical afterwards.
* **Limits of the method:** tests were written by the author of the code (shared blind spots); LiteSVM runs with signature verification OFF (Solana
  runtime checks are assumed, not tested); the reviewers were the same model family; mutation testing measures the tests, not the design.
* **Constraints:** everything ran offline; `cargo audit` / `cargo deny` / yanked-crate checks could NOT run (put in the deploy checklist for Rovik).

## 6. R-1..R-7, the NEITHER rows and the money bound (measured)
**R-1 measured** (`tests-rs/tests/vault_boundary.rs`, real vault fixture, launch values: delay 172,800 s, cap 100,000,000,000 micro-USD per 86,400 s window):
* compromised evaluator, veto NOT used, one record chain of a $100k account: 4 claims of 8,000,000,000 = **32,000,000,000 micro-USD = 32.0000 % of S**; the same 32.0000 % for all 10 tiers; the largest chain ($200k tier) is **64,000,000,000** ($64,000), as DESIGN 10.6 says. The size of the invented profit is irrelevant (+$999,000 pays 0.08 S). A fail and reset does not extend the chain (the vault copies the payout count).
* **with the veto used on every pass** (6 fabricated passes vetoed at 4 different moments): **0 micro-USD** paid; the daily window untouched; `vetoes` = 6.
* across many accounts, no veto, the cap in force: 14 accounts paid 448,000,000,000 (14 x 0.32 S), no window above the cap; the sector bound is **cap x (D + 1) over D days** (fixed windows allow a burst at each end); the attacker's outlay per chain is price + 0.4 % fee ($862.44 on the $100k tier).
* so at the launch cap a compromised evaluator with no veto can queue about **$100,000 of claims per full day** whatever the number of accounts (it needs a pipeline of at least 25 accounts to use the whole cap). **The 32 % bound is real and the veto reduces it to zero, but only if both admins are awake and the watchdog is running.**

| risk | restated, with what the code lets me measure |
|---|---|
| R-1 evaluator wrong or compromised | above: 32 % of size per chain, $100k/day at launch values, 0 with the veto. A wrongful FAIL has no on-chain remedy: one Fee event of any size up to i64::MAX plus a Fail fails any honest account (observation O-1 of the A-18 fragment); the loss for the trader is the reset price (e.g. $859 to $1,117 on $100k) or the whole account price. |
| R-2 omitted breach / dropped sample | cannot be proven on chain; the verifier cannot see it without a second recorder (NEITHER row 1). |
| R-3 evaluator outage | liveness only; vault idle clocks keep running (7 days) - and a pass delay above 7 days is lost (F-30). |
| R-4 oracle error or compromise | same bound as R-1; proof signatures are not checked on chain (R-7). |
| R-5 admin free feed remap | either admin alone can remap a feed or set max_age_secs up to 65,535 s with no delay (A-ADM-1); the bound is the same as R-1; the verifier's replay then goes MISMATCH on an honest history (F-19). |
| R-6 both admins unreachable for 2 days | a fake pass finalizes; bounded by cap and vault as above. |
| R-7 signatures not verified on chain | true: no instruction verifies an ed25519 signature; the source byte of a proof is not bound to the market's source (reviewer claim V1, accepted under R-7). |

**NEITHER list** (accepted by the program AND VALID for the verifier; handover/trust-matrix.md): (1) a sample that caused a breach dropped from the archive, breach omitted (no second recorder): money
terms = a position the trader should have lost stays open; the worst case is a pass built on it, bounded by R-1; (2) a market order executed at an older sample inside max_age (worse price): bounded by
the price move within max_age_secs (15 to 45 s at launch) times the order size, per order; **the favourable direction is the open finding F-08**; (3) a trader's market order ignored (no fill, intent on file): censorship, no money moves; (4) a triggered pending order in an
unpriced market that the evaluator does not fill: this is the rule itself (decision 64), not an attack.

## 7. Residual risks this suite cannot cover
* **Receive-time oracle weakness** (decisions 54 to 57): the proof time is the evaluator's receive time, so the evaluator chooses which real sample backs an event; max_age bounds the slack (F-08).
* **GMX signed blob with a null signer**: source 3 has no real authenticity today; only the sha256 digest of the blob is compared, and no signature is checked anywhere in the repo.
* **Stork / Pyth not built**: no signed on-chain price verification exists (R-7, A-ORA-1).
* **Signatures not verified on chain**: neither price proofs nor trader intents.
* **Evaluator hot key and its rotation runbook** (OPEN_QUESTIONS #11): the whole bound in section 6 assumes the key is guarded and rotated within hours.
* **A second, independent price recorder** is required for R-2 and does not exist.
* **OPEN_QUESTIONS #8** (veto policy) and **#9** (wrongful fail remedy) are policy: nothing in code helps.
* **The 10 pending orders / 8 positions limits** are off chain (evaluator only; the program has no position book: a Close of a position nobody opened with an invented entry price is accepted).
* **Single-key pause**: one admin key can pause the sector for ever (unpause needs both) - accepted under A-16 / DESIGN 14 but it is a one-key denial of service.
* **LiteSVM runs with signature verification off**: the Solana runtime's own signer checks are assumed; the single real-CPI test (attacker program) shows the privilege-escalation refusal.
* **Hand-decoded vault layouts** (`vault_view.rs`) and the vault fixture commit 9a5c179: any vault change can break reset/release (F-33); the vault source was not re-audited.
* **Deployment**: the `localnet` feature compiles public admin keys and mock proofs into a .so; only discipline and the deploy checklist (sha256 of the default build) stop the wrong build being deployed (reviewer claim AUTH-05, accepted).
