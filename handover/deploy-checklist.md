## `register_product` / `update_product_config` (both vault admins)
- `product_program_id` = the real program id (placeholder `9NAdnJ7ySQqPYuPKu6d6wCbcaHHMnzwFT6xEcRfXX2a7` replaced, keypair generated locally, never printed or committed).
- `reset_price_bps = [10000, 11500, 12000, 12750, 13000]`: basis points of the CURRENT tier price, indexed by the 0-based phase the trader failed in (type `Vec<u16>`, values above 10000 are intended). Never a size-based table such as `[100, 150]`.
- `challenge_sizes` = the rule set's ten tiers (size, cost) exactly, with **unique sizes**. Two tiers of one size with different costs make the vault answer `InvalidChallengeTier` forever for that size; the sector helper refuses any duplicate size.
- **Never reprice or remove a tier while Failed records exist.** A reset follows the tier cost registered now, not what the trader paid: repricing changes, and removing blocks, every pending reset of that size. (Restated for M8: `reset_account` reads the registry at the moment of the call. A removed tier is refused by the sector with `ResetTierInvalid` before any CPI, a duplicate size with the same error, a ladder shorter than the failed phase with `ResetPhaseOutOfRange`; a repriced tier is simply followed, the trader pays the new price. The ladder must have FIVE entries or the phases beyond it cannot be reset.)
- `reset_account` needs about 125,000 to 145,000 compute units for an ordinary key and 158,200 for the worst key found (M11, handover/module-11.md: the vault's `deposit_reset` is about 42,000 of it; the spread comes from the PDA bump searches of the trader's keys). It fits the default 200,000-unit limit; clients should ask for 200,000 explicitly (the asserted ceiling is 182,000). `open_account`: up to 135,595 (ceiling 156,000). Every other instruction needs no budget instruction at all; `post_journal` and `report_fail` are close to the 1,232-byte limit (1,181 and 1,149 bytes in the worst case).
- `max_payout_count` = **4** (one payout per phase 2 to 5; the local graduation assumes it).
- `fee_split_bps` (the harness uses 6500; the real number is Rovik's); mints = the vault's USDC and USDT.

## Program and config
- Deploy only the DEFAULT build (real admin keys); never `--features localnet`. `scripts/anchor-build-checked.sh` clean, record the sha256.
- `constants/admin.rs` real SL8 and Rov keys (equal to the vault's); upgrade authority 2-of-2 (decision 30).
- `init_config` (both admins): `evaluator`, `vault_program` = real vault id, `sl8_wallet` (needs a token account of each accepted mint for the 0.4% fee), `pass_delay_secs` 172,800, `window_secs` 86,400, `max_payout_per_window` = 100,000,000,000 micro-USD (decision 37).
- Markets and rule set 1: generated and verified by `tools/launch-config` from `config/launch-markets.toml` (handover/launch-config.md): `create_market` x 21 in id order from `config/launch.json`, then `create_ruleset` v1 ONLY after the final `spread_e6` exist (the commissions are final: 0.02 % per side, 200 e6; 21 PENDING spread flags today, decision 72; `launch-config verify --production` is the gate). A market added after launch needs a new rule set version and stays disabled until it is current (older accounts would trade it at a zero spread, see launch-config.md). Holidays, half days and daylight-saving changes are `update_market` window changes.
- **Adding a market after launch (decision 64, P21).** A rule set is immutable and `spread_e6` is indexed by market id, so a market created after rule set version N has a half-spread of 0 in version N and every older version, and accounts of those versions CANNOT open or add to a position there (`MarketUnpriced`, 6109, program; the evaluator refuses the order; the verifier flags the fill). Procedure: create the market with `status = 0`, publish the NEW rule set version that gives it a non-zero half-spread, enable the market when that version is the current one; only accounts opened under that version (or later) trade it. Old accounts keep trading every market their rule set prices. Before `create_ruleset` of any version run `launch-config verify` (it refuses a zero half-spread for every market id).
- Evaluator operations, rent and fees, open policy items: see `module-7.md`.

## M12 audit additions (handover/AUDIT_REPORT.md section 10)

- **Online on Rovik's Mac** (the audit machine had no network; F-39, decision 67): `cargo install cargo-audit cargo-deny`, add a `deny.toml`, then run `scripts/online-supply-chain-check.sh` (it runs `cargo audit` and `cargo deny check` for the root workspace, `tests-rs` and `tools/launch-config`; it was written but NOT run on the audit machine). - Build with `--locked` (done in `scripts/build-test-so.sh` as `cargo build-sbf ... -- --locked`, in `scripts/test-engine.sh`, and in `scripts/anchor-build-checked.sh`, which cannot pass the flag through `anchor build` and instead runs `cargo metadata --locked` before and checks that Cargo.lock is byte-identical after the build; F-39). `rust-toolchain.toml` pins the host toolchain **1.94.0** (the rustc the audit ran on; the SBF program is compiled by the platform-tools rustc of the installed Solana/Agave: record its version, `cargo build-sbf --version`, with the hash). On a machine WITHOUT network that has only another toolchain, rustup would try to download 1.94.0: run with `RUSTUP_TOOLCHAIN=stable` there. The localnet `.so` (public admin keys, mock proofs) must never be deployed: check `solana-verify`/hash and that the admin keys inside the deployed binary are the real ones.
- **Evaluator key**: hardware-backed or KMS signer; written rotation runbook (both admins `set_evaluator`); rotate within hours of any suspicion; practice the rotation once on devnet. The 32 % money bound only holds while this key is guarded.
- **Watchdog**: run `setl8-verify watch` on every `PassRequested`/`PassConfirmed` and alert both admins inside the first hour; both admins must be able to sign a veto inside two days, weekends included. Check that `watch` exits 2 (not 0) on an unreadable feed (fixed in M12; alert on exit code != 0).
- **Second, independent price recorder** (DESIGN 4.5): without it R-2 is open and the NEITHER rows stay NEITHER.
- **Upgrade key (A-11)**: authority is the 2-of-2 multisig, deploy keypair destroyed, alerts on any Upgrade/SetAuthority, burn decision dated after the independent audit. **Wallet cap evasion (A-13)** is an off-chain policy item (KYC, funding-source review).
- **Rule sets**: read back every rule set before `create_ruleset` (tier sizes must be whole dollars; the program now refuses others).
- **Pass delay (F-30, decision 67)**: `pass_delay_secs` is limited to 1 to 6 days by the program (`init_config` and `set_limits`, `InvalidLimits` otherwise) because the vault abandons a record idle for 7 days. Duty: the evaluator calls `touch_activity` at least once during every pending (confirmed) pass, so idle time before the confirmation plus the delay cannot reach 7 days.
- **Config read-back before the upgrade authority moves (F-31, ACCEPTED, decision 67)**: `init_config` accepts any non-default `vault_program` and `sl8_wallet`, and nothing can change them or the admin pair afterwards (a mistake needs a 2-of-2 program upgrade). Duty, on devnet AND on mainnet, BEFORE the upgrade authority is handed to the multisig: read the `SectorConfig` account and check by eye that `vault_program` is the real vault id, `sl8_wallet` is the real SL8 wallet (with the token accounts), and `admin_a` / `admin_b` are the two real admin keys (equal to the vault's); also read `evaluator`, `pass_delay_secs`, `window_secs`, `max_payout_per_window`. Reason for accepting: the values are set once by the two admins in one signed transaction; a code check cannot know which address is the real one.
- **Accepted, no code change (decision 67)**:
  - F-28 (`fail_for_violation` / `report_fail` revert when the vault already flipped the record to Abandoned): liveness only, no money moves wrongly; `touch_activity` / `release_account` resolves it. Duty: the evaluator keeps activity fresh (also needed for F-30) and the operator watches for accounts stuck on this error.
  - F-29 (a lying outer Borsh length prefix aborts `post_journal` / `report_fail` with an allocation panic): it fails only the sender's own transaction, state unchanged, about 2,300 CU. Duty: the evaluator builds the batch itself and never sends a length it did not compute (evaluator-only, no one else can make the evaluator's transaction fail).
  - F-33 (hand-decoded vault layouts): pinned by `tests-rs/tests/vault_layout_pin.rs` (sha256 of the vault fixture and the byte offsets and discriminators `vault_view.rs` reads, checked against real vault accounts). Duty: before upgrading to a newer vault build, rebuild the fixture from that build, update `VAULT_FIXTURE_SHA256` and run the suite; the pin test fails first if the layout moved.
  - F-34 (`engine::consts::frac` / `static_floor` panic above about 8.5e14 micro-USD): no production caller; marked `#[deprecated]` with a comment. Duty: none, new code uses `account::frac_exact`.
  - F-38 (`init_if_needed` at two sites): DESIGN 6.2 requires it and the re-initialisation guard was read in anchor-syn 0.32.2; the `account_hygiene.rs` reinit rows test it. Duty: re-check the guard if the Anchor version is ever changed.
- **Failed + held accounts (F-32, decision 67 amendment, P25c)**: `report_fail` on a held account leaves it Failed + held; the trader can neither reset nor close it (`ReviewPending`, 6110) and the wallet cannot be banned (`WalletHasHeldAccount`) until BOTH admins decide: `release_hold` (an ordinary resettable failure) or `fail_for_violation` (marker, wallet banned, never resettable). Duty: the watchdog (DESIGN 13.3) alerts both admins on every `AccountFailed` of an account that is still held and on any Failed + held account older than 24 hours; the admins resolve each one. The evaluator and the verifier were NOT changed for this (P25b); the verifier reads `account_failed` followed by `hold_released` or `violation_fail` without a new vocabulary.
- **Verifier gaps after P25b (decision 68)**: the verifier now prices events with a named sample, validates the archive, understands cancelled passes, abandoned accounts and admin market changes, and says NOT ANCHORED TO THE CHAIN unless it was given a chain snapshot. Duties: (1) the indexer that builds the events file must write the `pass_cancelled`, `account_abandoned`, `market_feed_changed` and `market_status_changed` lines (verifier-formats.md section 1) at the position it saw them; (2) the watchdog runs `watch` for the hourly alert and `account --snapshot` (whole log) for the final word; (3) keep an eye on the evaluator's sample counters (`Stats::samples_future`, `samples_stale`, `samples_out_of_order`): a rising count means a bad upstream clock or feed.
- **F-25 deferred (P25b)**: lifecycle events (hold, release, phase) are outside the hash chain, so the verifier orders them by file position and block time; a Fill posted after a release but dated before it can be judged wrongly (a false MISMATCH, never a false VALID). Reason: the fix is a v2 log format (a sequence number on those events) and a program change. Duty: a MISMATCH around a hold/release pair is read by a human before it is acted on.
- **F-16 resolved (P26, decision 69)**: the program takes `Close{Fail}` events after a quick-limit overshoot in `report_fail`, so an account with several open positions can always be ended when the failing batch fits the batch limits (at most 8 events and 3 distinct proofs: the crossing close and at most 5 forced closes, then the `Fail` and the `Meta`; closes in at most three markets). Duties: (1) the operator still watches `Stats::unpostable` (a group that does not fit those limits, asserted 0 over the campaigns, which cannot produce it); an account that stops posting with more than six open positions or positions in more than three markets at a quick-limit fail is the case; (2) the watchdog's verifier run flags a forced close nothing justifies (`ForcedCloseUnjustified`, `FalseFailMarks`) and a `Close{Fail}` of a position that is not open (`PositionMismatch`): both are MISMATCH and a human reads them; (3) the program does not track positions, so a compromised evaluator can add `Close{Fail}` events to a failing batch that the program takes (trust matrix, P26 changes); the account ends Failed in the same batch.

## Devnet rehearsal (P23, decision 70, handover/devnet-rehearsal.md)
The rehearsal of the frozen program with the real vault ran on a LOCAL validator (Agave 4.0.2); the devnet part waits for SOL (the public faucet refused: about 13.1 SOL are needed, 11.6 of them for the two deployments). What it exposed for the real deployment:
* **Compute (D-01, high): resolved OFF-program by P27 (decision 71), see "Compute budget: what the backend MUST do" below.** An event costs about 17,300 CU on the runtime (12,539 inside the `emit_cpi!` self-call) against 10,000 to 12,000 in LiteSVM; a legal `report_fail` of 8 events and 3 proofs FAILS with ComputationalBudgetExceeded at the default 200,000 limit. The fix needs no program change: an explicit `SetComputeUnitLimit` fitted on the real runtime, a model in the evaluator, a measured table.
* **Order of work on devnet:** keys, build, fund (13.07 SOL; the faucet is rate limited, use the browser faucet for the upgrade authority), deploy the vault and the program (`solana program deploy --max-len` the exact size), `register_product` BEFORE the first `open_account`, then `init_config`, 21 markets, rule set v1; the vault's SL8 admin token accounts for BOTH mints must exist before the first fee.
* **Admin keys:** a rehearsal build swaps the compiled-in admin keys for throwaway ones; the checklist item "deploy only the DEFAULT build" stands and the real-key build is NOT rehearsed.
* **Reset after a violation:** `reset_account` answers `WalletBanned` first and `ViolationNoReset` only after `unban_wallet`; support text must say so.
* **Verifier and watchdog:** the chain's events decode into the verifier's format without change; the watchdog's RPC needs the account's whole history (`getSignaturesForAddress` and `getTransaction`); a pruned RPC reads as "no opened line". The verifier does not know proof source 255 (mock): never run the watchdog on a localnet-built deployment's mock-traded accounts.
* **Time:** a journal event cannot be dated before the account exists or more than 2 s after the block time: an evaluator must not run ahead of the cluster clock (the driver posts a batch when the MEASURED block time has reached its `Meta` and retries `TimeInFuture`).
* **Resume:** the rehearsal's state is `state.json` (public data); `run` is the same command on day 1 and day 2.

## Compute budget: what the backend MUST do (P27, decision 71; handover/backend-compute-contract.md)
The program is unchanged; the evaluator and its transactions carry the fix. Measured on a validator (Agave 4.0.2, `handover/cu-runtime.json`, 102 shapes, three runs each): `post_journal` 188,799 CU and `report_fail` 224,440 CU at 8 events and 3 proofs, `reset_account` 154,289; LiteSVM shows 125,290, 151,284 and 158,203 and is only the regression harness.
* **The 200,000 default is NOT enough** for `post_journal` and `report_fail` at 7 to 8 events (up to 203,578 CU at 7 events and 3 proofs, up to 224,440 at 8, on the validator). EVERY `post_journal` and `report_fail` transaction MUST carry `SetComputeUnitLimit` = `Batch.cu_limit` (the evaluator's `compute::recommended_cu_limit`: the measured worst case for the shape x 1.20, rounded up to 1,000, at most 1,400,000; the largest a batch asks for is 270,000). `reset_account` (154,289 measured) and the other trader instructions that depend on the key (`open_account`, `finalize_pass`, `touch_activity`, `release_account`) carry 400,000. Never request more than 1,400,000.
* **Transaction size.** The limit instruction adds 40 bytes (a `SetComputeUnitPrice` 12 more). The evaluator counts it: a transaction never exceeds 1,232 bytes (`Batch.tx_bytes`). A quick-limit failure group that cannot be split (decision 69) and does not fit a legacy transaction (three forced closes in three source-3 markets: 1,244 bytes) comes with `Batch.tx_format == V0Lookup`: the backend MUST send a version-0 transaction and keep an address lookup table with the program's config, every rule set, the event authority, the sector authority, the vault program, the vault's product registry and every market (extend it in the same operation as `create_market` and `create_ruleset`; never deactivate it). Checklist item for the launch: create the table, extend it, send one `V0Lookup` batch on devnet.
* **Re-measure.** The table is from a local validator. Run `scripts/devnet-rehearsal.sh selftest measure` against the validator version you deploy to, run the devnet rehearsal against devnet, and again against mainnet-beta BEFORE launch because runtime versions differ; commit the new `handover/cu-runtime.json` and regenerate the tables (`cargo test -p setl8-lev-evaluator print_tables -- --ignored --nocapture`): the evaluator's `compute` tests and `tests-rs/tests/budget_runtime.rs` fail until you do. Proofs of the real sources 2, 3 and 4 were measured as mock proofs (source 255): LiteSVM shows up to 8 % between sources, inside the 20 % margin; the real program id changes the bump searches of the key-dependent instructions.

## Owner's fixed costs (P24a, decision 72)
* The rule set for mainnet = the owner's costs of `config/launch-markets.toml` (commission 0.02 % per side = 200 e6 on every class; half-spread base 100 e6 = 1 bp of price per side on every market, "1 pip each side" read that way; the first reading, 300 e6 and 50 e6, was revised by Rovik the same day before any deploy) PLUS the oracle-noise floor of P24b: half-spread = max(owner base, floor), raised per market where the Hyperliquid oracle noise is larger (6 to 12 bp against the book mid). Until P24b has run, all 21 spread flags stay and `launch-config verify --production` fails (that is the gate: do NOT create the rule set earlier, it is immutable).
* NEWS SPREAD IS OPEN: the owner asked for 20 pips around news; the rule set has one fixed half-spread per market and the program is frozen, so nothing implements it. Decision pending.
* If "1 pip" was meant per class pip size, or the commission is 0.02 % per round trip (100 e6 per side) instead of per side, change the numbers before `create_ruleset`; after it, a new rule set version is needed.
