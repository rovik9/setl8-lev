# Deploy checklist (consolidated)

Values and checks that live outside the code; none is set by this repo. The per-module lists (`module-7.md` "Deploy checklist" and the others) stay as the history of where each item came from. Last updated 2026-10-17 (decisions 58 to 61).

## Vault and shared-interfaces
- Vault: core commit **9a5c179 or later** (the reset price is a percentage of the TIER price from this commit on). Older vaults price a reset off the account size.
- `setl8-shared-interfaces`: pinned BY COMMIT (`rev = "3b0580c47979387e03f11c280d93a5870c66cd3e"`, which is the v0.5.0 tag commit) in `programs/setl8-lev-trading/Cargo.toml` and `tests-rs/Cargo.toml` (F-39, decision 67); both lock files resolve to that commit. A tag can be moved, a commit hash cannot.
- Test fixture `tests-rs/fixtures/core_vault.so` (git-ignored): the vault's localnet build (`scripts/build-test-so.sh` in a clean clone at 9a5c179), sha256 `42c6267008ca25cfd7b71792f3797307292049d91420dbba8fe07dc3098c89a6`, asserted by `VAULT_FIXTURE_SHA256` in `tests-rs/tests/common/vault.rs`.

## `register_product` / `update_product_config` (both vault admins)
- `product_program_id` = the real program id (placeholder `9NAdnJ7ySQqPYuPKu6d6wCbcaHHMnzwFT6xEcRfXX2a7` replaced, keypair generated locally, never printed or committed).
- `reset_price_bps = [10000, 11500, 12000, 12750, 13000]`: basis points of the CURRENT tier price, indexed by the 0-based phase the trader failed in (type `Vec<u16>`, values above 10000 are intended). Never a size-based table such as `[100, 150]`.
- `challenge_sizes` = the rule set's ten tiers (size, cost) exactly, with **unique sizes**. Two tiers of one size with different costs make the vault answer `InvalidChallengeTier` forever for that size; the sector helper refuses any duplicate size.
- **Never reprice or remove a tier while Failed records exist.** A reset follows the tier cost registered now, not what the trader paid: repricing changes, and removing blocks, every pending reset of that size. (Restated for M8: `reset_account` reads the registry at the moment of the call. A removed tier is refused by the sector with `ResetTierInvalid` before any CPI, a duplicate size with the same error, a ladder shorter than the failed phase with `ResetPhaseOutOfRange`; a repriced tier is simply followed, the trader pays the new price. The ladder must have FIVE entries or the phases beyond it cannot be reset.)
- `reset_account` needs about 125,000 to 145,000 compute units for an ordinary key and 158,200 for the worst key found (M11, handover/module-11.md: the vault's `deposit_reset` is about 42,000 of it; the spread comes from the PDA bump searches of the trader's keys). It fits the default 200,000-unit limit; clients should ask for 200,000 explicitly (the asserted ceiling is 182,000). `open_account`: up to 135,595 (ceiling 156,000). Every other instruction needs no budget instruction at all; `post_journal` and `report_fail` are close to the 1,232-byte limit (1,181 and 1,149 bytes in the worst case).
- `max_payout_count` = **4** (one payout per phase 2 to 5; the local graduation assumes it).
- `fee_split_bps` (the harness uses 6500; the real number is Rovik's); mints = the vault's USDC and USDT.

## Program and config
- Deploy only the DEFAULT build (real admin keys); never `--features localnet`. `scripts/anchor-build-checked.sh` clean, record the sha256.
- `constants/admin.rs` real SL8 and Rov keys (equal to the vault's); upgrade authority 2-of-2 (decision 30).
- `init_config` (both admins): `evaluator`, `vault_program` = real vault id, `sl8_wallet` (needs a token account of each accepted mint for the 0.4% fee), `pass_delay_secs` 172,800, `window_secs` 86,400, `max_payout_per_window` = 100,000,000,000 micro-USD (decision 37).
- Markets and rule set 1: generated and verified by `tools/launch-config` from `config/launch-markets.toml` (handover/launch-config.md): `create_market` x 21 in id order from `config/launch.json`, then `create_ruleset` v1 ONLY after the real `spread_e6` and `commission_e6` exist (29 PENDING flags today; `launch-config verify --production` is the gate). A market added after launch needs a new rule set version and stays disabled until it is current (older accounts would trade it at a zero spread, see launch-config.md). Holidays, half days and daylight-saving changes are `update_market` window changes.
- **Adding a market after launch (decision 64, P21).** A rule set is immutable and `spread_e6` is indexed by market id, so a market created after rule set version N has a half-spread of 0 in version N and every older version, and accounts of those versions CANNOT open or add to a position there (`MarketUnpriced`, 6109, program; the evaluator refuses the order; the verifier flags the fill). Procedure: create the market with `status = 0`, publish the NEW rule set version that gives it a non-zero half-spread, enable the market when that version is the current one; only accounts opened under that version (or later) trade it. Old accounts keep trading every market their rule set prices. Before `create_ruleset` of any version run `launch-config verify` (it refuses a zero half-spread for every market id).
- Evaluator operations, rent and fees, open policy items: see `module-7.md`.

## M12 audit additions (handover/AUDIT_REPORT.md section 10)
- **Independent human review BEFORE real money.** The M12 audit is a self-audit by the builder; it is not a substitute.
- **Online on Rovik's Mac** (the audit machine had no network; F-39, decision 67): `cargo install cargo-audit cargo-deny`, add a `deny.toml`, then run `scripts/online-supply-chain-check.sh` (it runs `cargo audit` and `cargo deny check` for the root workspace, `tests-rs` and `tools/launch-config`; it was written but NOT run on the audit machine). Look at yanked crates and read the result before every deploy.
- Build with `--locked` (done in `scripts/build-test-so.sh` as `cargo build-sbf ... -- --locked`, in `scripts/test-engine.sh`, and in `scripts/anchor-build-checked.sh`, which cannot pass the flag through `anchor build` and instead runs `cargo metadata --locked` before and checks that Cargo.lock is byte-identical after the build; F-39). `rust-toolchain.toml` pins the host toolchain **1.94.0** (the rustc the audit ran on; the SBF program is compiled by the platform-tools rustc of the installed Solana/Agave: record its version, `cargo build-sbf --version`, with the hash). On a machine WITHOUT network that has only another toolchain, rustup would try to download 1.94.0: run with `RUSTUP_TOOLCHAIN=stable` there. Record the sha256 of the DEFAULT (real-key) `.so` and compare it with the verifiable build before every deploy or upgrade. The localnet `.so` (public admin keys, mock proofs) must never be deployed: check `solana-verify`/hash and that the admin keys inside the deployed binary are the real ones.
- **Evaluator key**: hardware-backed or KMS signer; written rotation runbook (both admins `set_evaluator`); rotate within hours of any suspicion; practice the rotation once on devnet. The 32 % money bound only holds while this key is guarded.
- **Watchdog**: run `setl8-verify watch` on every `PassRequested`/`PassConfirmed` and alert both admins inside the first hour; both admins must be able to sign a veto inside two days, weekends included. Check that `watch` exits 2 (not 0) on an unreadable feed (fixed in M12; alert on exit code != 0).
- **Second, independent price recorder** (DESIGN 4.5): without it R-2 is open and the NEITHER rows stay NEITHER.
- **Upgrade key (A-11)**: authority is the 2-of-2 multisig, deploy keypair destroyed, alerts on any Upgrade/SetAuthority, burn decision dated after the independent audit. **Wallet cap evasion (A-13)** is an off-chain policy item (KYC, funding-source review).
- **Rule sets**: read back every rule set before `create_ruleset` (tier sizes must be whole dollars; the program now refuses others).
- **Pass delay (F-30, decision 67)**: `pass_delay_secs` is limited to 1 to 6 days by the program (`init_config` and `set_limits`, `InvalidLimits` otherwise) because the vault abandons a record idle for 7 days. Duty: the evaluator calls `touch_activity` at least once during every pending (confirmed) pass, so idle time before the confirmation plus the delay cannot reach 7 days.
- **Config read-back before the upgrade authority moves (F-31, ACCEPTED, decision 67)**: `init_config` accepts any non-default `vault_program` and `sl8_wallet`, and nothing can change them or the admin pair afterwards (a mistake needs a 2-of-2 program upgrade). Duty, on devnet AND on mainnet, BEFORE the upgrade authority is handed to the multisig: read the `SectorConfig` account and check by eye that `vault_program` is the real vault id, `sl8_wallet` is the real SL8 wallet (with the token accounts), and `admin_a` / `admin_b` are the two real admin keys (equal to the vault's); also read `evaluator`, `pass_delay_secs`, `window_secs`, `max_payout_per_window`. Reason for accepting: the values are set once by the two admins in one signed transaction; a code check cannot know which address is the real one.
- **Accepted, no code change (decision 67)**:
  - F-28 (`fail_for_violation` / `report_fail` revert when the vault already flipped the record to Abandoned): liveness only, no money moves wrongly; `touch_activity` / `release_account` resolves it. Duty: the evaluator keeps activity fresh (also needed for F-30) and the operator watches for accounts stuck on this error.
  - F-29 (a lying outer Borsh length prefix aborts `post_journal` / `report_fail` with an allocation panic): it fails only the sender's own transaction, state unchanged, about 2,300 CU. Duty: the evaluator builds the batch itself and never sends a length it did not compute (evaluator-only, no one else can make the evaluator's transaction fail).
  - F-33 (hand-decoded vault layouts): pinned by `tests-rs/tests/vault_layout_pin.rs` (sha256 of the vault fixture and the byte offsets and discriminators `vault_view.rs` reads, checked against real vault accounts). Duty: before upgrading to a newer vault build, rebuild the fixture from that build, update `VAULT_FIXTURE_SHA256` and run the suite; the pin test fails first if the layout moved.
  - F-34 (`engine::consts::frac` / `static_floor` panic above about 8.5e14 micro-USD): no production caller; marked `#[deprecated]` with a comment. Duty: none, new code uses `account::frac_exact`.
  - F-38 (`init_if_needed` at two sites): DESIGN 6.2 requires it and the re-initialisation guard was read in anchor-syn 0.32.2; the `account_hygiene.rs` reinit rows test it. Duty: re-check the guard if the Anchor version is ever changed.
- **Failed + held accounts (F-32, decision 67 amendment, P25c)**: `report_fail` on a held account leaves it Failed + held; the trader can neither reset nor close it (`ReviewPending`, 6110) and the wallet cannot be banned (`WalletHasHeldAccount`) until BOTH admins decide: `release_hold` (an ordinary resettable failure) or `fail_for_violation` (marker, wallet banned, never resettable). Duty: the watchdog (DESIGN 13.3) alerts both admins on every `AccountFailed` of an account that is still held and on any Failed + held account older than 24 hours; the admins resolve each one. The evaluator and the verifier were NOT changed for this (P25b); the verifier reads `account_failed` followed by `hold_released` or `violation_fail` without a new vocabulary.
- Open verifier gaps (F-08 to F-14 of the report) mean the verifier's VALID is weaker than DESIGN 4.6 implies: until they are fixed, treat VALID as "no problem found by this tool", not as proof.
